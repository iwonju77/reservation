## 구현 범위와 출시 단계

우선 한 매장의 예약·좌석 관리를 완성한다. 직원 관리자 화면은 한국어를 기본으로 번체중문 전환을 제공하고, 고객 웹은 번체중문 기본·한국어 선택으로 설계한다. 실제 운영 언어와 문구는 공개 전에 확인한다.

| 단계 | 제공 기능 | 운영 조건 |
|---|---|---|
| A: 직원 내부 운영 | 테이블·영업시간·정책, 직원 예약, 현장 방문, 좌석 배정, 변경·취소·방문 처리 | 실제 테이블·영업일 검증, 직원 교육, 백업 복구 및 장애 절차 검증 |
| B: 고객 웹 공개 | 다국어 고객 예약, 본인 예약 관리, 알림, 필요한 경우 예약금·환불 | 활성 정책이 요구하는 외부 서비스의 실연동 검증 완료 |
| C: 운영 확장 | 대기 자동 제안, 전화 AI, 추가 알림·결제 업체 | 각 연동별 통합 테스트와 운영자 인수 완료 |

예약금이 필수인 정책을 결제 연동 없이 공개하지 않는다. 전화 AI는 B 이후에 활성화한다. 기능은 구현하되 자격증명이나 계약이 없으면 비활성 상태와 구체적인 미검증 사유를 기록한다. 단계 A도 실서비스이므로 데이터 보호·백업·복구는 생략하지 않는다.

## 첫 번째 기능 구현 범위

개발 데이터로 다음 흐름이 실제 PostgreSQL에서 끝까지 작동하게 만든다.

1. 개발용 직원 계정으로 로그인한다.
2. 테이블과 결합 조합, 요일별 영업시간, 이용시간·정리시간을 등록한다.
3. 직원이 날짜·인원을 조회하고 예약을 확정한다. 초기 fixture는 예약금 없는 정책을 명시한다.
4. 같은 시간의 같은 테이블을 다시 예약하면 충돌을 표시한다.
5. 예약을 변경·취소하거나 도착·착석·퇴석 처리한다.
6. 새로고침과 서비스 재시작 후에도 예약·점유·감사 이력이 보존된다.

직원 예약 MVP에서도 인증·권한, 정책 스냅샷, DB 중복 점유 제약, 멱등 명령은 포함한다. 외부 업체 없이 실행 가능한 내부 기능부터 검증한다.

## 화면 설계

| 화면 | 주요 표시·작업 |
|---|---|
| 직원 로그인 | 개인 계정, 세션 만료, 비활성 계정 차단 |
| 오늘의 예약 | 영업일·구역 필터, 시간순 목록, 승인 대기·지각·이용 초과 표시 |
| 테이블 현황 | 예약상 점유와 실제 착석 구분, 다음 예약, 정리 중 상태 |
| 예약 등록·상세 | 시간·인원·연락처·정책 요약, 변경 견적, 취소, 방문 처리, 이력 |
| 운영 설정 | 테이블·결합·영업시간·특별일·예약 정책, 적용일·변경 영향 |
| 처리 필요 목록 | 승인 만료 임박, 충돌, 연락 필요, 결제 불일치·환불 실패 |
| 고객 예약 | 날짜·인원 → 가능 시간 → 연락처·조건 확인 → 현재 상태 |
| 고객 예약 관리 | 안전한 세션, 조회·변경·취소, 금액·환불 상태 |

관리자는 SQL·내부 상태 코드 대신 매장 운영 용어를 본다. 예: `PENDING_APPROVAL`은 ‘직원 승인 대기’, `CONFIRMED`는 ‘예약 확정’으로 표시한다.

## 기술 기준안

- TypeScript, Next.js 고객·관리자 웹 및 API, PostgreSQL, SHA-256 검증 SQL migration, 별도 Node.js worker.
- pnpm workspace: `apps/web`, `apps/worker`, `packages/domain`, `packages/db`, `packages/providers`, `packages/shared`.
- Vitest 단위 테스트, 실제 PostgreSQL 통합 테스트, Playwright E2E.
- 초기에는 단일 매장으로 운영하되 주요 테이블과 권한에 `restaurant_id`를 포함한다.
- 첫 단계에서 현재 지원되는 안정 버전과 상호 호환성을 확인하여 정확한 버전을 잠그고 lockfile을 커밋한다.
- 배포는 웹과 상시 worker, 관리형 PostgreSQL을 실행할 수 있는 환경을 전제로 한다. 특정 호스팅 계약은 가정하지 않는다.

## 서비스 책임과 기능 활성화

- 웹/API: 인증·입력 검증과 요청 처리. 예약 규칙은 `packages/domain`에서 평가한다.
- PostgreSQL: 영속 데이터·트랜잭션·점유 제약·작업 큐를 담당한다.
- worker: 임시 확보 만료·승인 기한 처리부터 먼저 구현하고 이후 알림·대사를 추가한다.
- 제공업체 모듈: 개발용 fake와 실제 Adapter를 명확히 구분한다.
- 매장별 `online_booking_enabled`, `payments_enabled`, `sms_enabled`, `waitlist_enabled`, `voice_ai_enabled`를 서버에서 검사한다. 개발 fixture 외에는 준비되지 않은 기능을 기본 OFF로 둔다.
- 결제 필수 정책인데 결제 연결이 미검증이면 정책 활성화 또는 접수 활성화를 거부하고 필요한 설정을 표시한다.

고객 예약의 확정 여부와 알림 성공 여부는 독립적으로 표시한다. 결제·전화 연동 준비가 안 되어도 직원용 내부 개발은 계속할 수 있다.

## 반드시 유지할 원칙

1. 웹·직원·전화 AI는 하나의 예약 도메인 서비스를 사용한다.
2. 좌석 중복 방지는 DB 제약조건으로 보장하며 직원 예외 처리도 이를 우회하지 않는다.
3. 예약 정책은 버전과 스냅샷을 저장하고, 이미 확정된 예약을 설정 변경만으로 바꾸지 않는다.
4. 예약·결제·환불·발송 상태를 분리한다. 결제 여부를 브라우저 화면으로 판단하지 않는다.
5. 외부 API 호출은 DB 트랜잭션 밖에서 수행한다. 이벤트와 요청의 중복 처리를 방지한다.
6. 설정값과 비밀값을 구분한다. 비밀값은 저장소·로그·감사 이력에 남기지 않는다.
7. 모의 테스트 성공, sandbox 성공, 실제 운영 연동 성공을 서로 구분한다.
8. 현장 운영자가 확인해야 할 정책은 기본 제안값으로 개발을 진행하고 공개 전에 확정한다.

## 전체 완료 정의

- 활성화할 기능에 대한 단계별 테스트와 현장 인수 시나리오가 통과한다.
- 데이터베이스 복구를 실제 수행하고 목표 복구 시간을 측정한다.
- 배포·마이그레이션·장애 대응·비밀정보 교체 절차가 문서화된다.
- 필수 외부 연동이 실제 계정과 허용된 테스트 수신처로 검증된다.
- 운영 책임자가 초기 정책, 고객 안내문, 환불 정책, 개인정보·녹취 보관 정책을 확정한다.
- 미완료 기능은 비활성화되며, 영향을 받는 고객 흐름이 노출되지 않는다.

문서만 생성하거나 화면만 동작하는 상태는 구현 완료가 아니다. 각 단계의 결과는 `05-progress.md`에 실제 실행 증거와 함께 기록한다.
