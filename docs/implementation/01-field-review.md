# 현장 운영 검토 및 결정사항

## 기존 설계에서 유지할 내용

관리자 설정, 테이블 결합, 요일별·특정일 영업, 정책 스냅샷, 변경 이력, 공통 예약 엔진, 제공업체 Adapter 구조를 유지한다. 다음 항목은 현장 운영에 필요한 보완이다.

## 보완사항과 구현 결정

| 항목 | 현장 문제 | 구현 결정 |
|---|---|---|
| 현장 방문 | 온라인 예약과 직원 접수가 같은 좌석을 사용 | 현장 방문도 예약 엔진을 통해 등록하고 `WALK_IN` 출처를 기록 |
| 지각 | 늦게 온 고객의 이용 종료 시각이 불분명 | 기본은 원래 종료 시각 유지. 직원 연장 시 다음 예약 충돌 검사와 사유 기록 |
| 이용시간 초과 | 예정 종료만으로 빈자리로 보일 수 있음 | 예약상 점유와 현재 착석 상태를 구분. 초과 경고·충돌 목록 표시, 실제 퇴석 확인 전 즉시 착석 안내 금지 |
| 조기 방문 | 현재 이용 중인 테이블에 배정될 수 있음 | 도착 상태와 착석을 구분하고, 조기 착석 시 시간 구간 변경을 검증 |
| 테이블 변경 | 다른 예약이나 결합 테이블과 충돌 | 새 배정을 먼저 검증하고 한 트랜잭션으로 이동 |
| 테이블 정비·고장 | 기존 예약의 좌석이 갑자기 사라짐 | 차단 전에 영향 예약을 제시하고 재배정 작업 목록 생성 |
| 휴무 변경 | 정책 스냅샷만으로 방문 불가 문제를 해결 못함 | 기존 예약을 자동 취소하지 않고 영향 목록·연락·변경·환불 작업 제공 |
| 직원 승인 | 승인 대기가 장기간 좌석 점유 | 승인 기한과 담당자 표시, 만료 경고·자동 해제 |
| 결제 지연 | 좌석 해제 후 결제가 성공할 수 있음 | 예약 자동 부활 금지, 결제 대사·환불 작업으로 전환 |
| 대기명단 | 큰 인원 또는 특정 시간 손님이 계속 밀림 | 조건 일치 고객 중 접수 순서. 수동 순서 변경에는 사유, 대기 경과시간 표시 |
| 알림 장애 | 예약은 성공했지만 고객이 문자를 못 받음 | 확정 화면·예약 관리 링크 제공, 관리자 재발송·연락 작업 표시 |
| 인터넷 장애 | 현장에서 접수와 방문 확인이 중단 | 제한된 당일 예약표와 수기 접수 절차, 복구 후 중복·충돌 확인하여 입력 |
| 직원 동시 편집 | 서로의 예약 변경을 덮어씀 | 예약 `version` 기반 충돌 응답과 최신 정보 재조회 |
| 야간 영업 | 날짜가 넘어가면서 예약이 사라짐 | 영업일과 실제 시각을 구분하고 익일 종료 지원 |
| 자동 처리 복구 | 잘못된 No-show 복구가 중복 예약 생성 | 좌석 재확보 가능 시에만 복구. 불가능하면 관리자 재배정 |

## 운영자 확정이 필요한 값

아래 값은 제안이며 실제 영업 규정으로 확정된 것이 아니다. 개발용 fixture와 운영 데이터를 구분한다.

| 설정 | 개발 기본안 | 확정 시점 |
|---|---|---|
| 시간대·통화 | Asia/Taipei / TWD | 최초 운영 데이터 등록 전 |
| 고객 언어 | 번체중문 기본, 한국어 선택 | 고객 웹 공개 전 |
| 고객 정보 | 이름·휴대전화·필요한 요청사항만 | 내부 운영 전 |
| 임시 좌석 확보 | 5분, 만료 전 고지 | 고객 웹 공개 전 |
| 직원 승인 기한 | 영업 중 30분 제안. 미운영 시간의 접수 정책 별도 확정 | 승인 기능 활성화 전 |
| 결제 기한 | 10분 제안, 제공업체 세션 만료와 조정 | 결제 활성화 전 |
| 정리시간 | 15분 제안 | 내부 운영 전 |
| 지각·No-show | 15분 후보 표시, 자동 No-show OFF | 내부 운영 전 |
| 단체 기준 | 8명 이상 승인 필요, 웹 접수 상한 8명 | 고객 웹 공개 전 |
| 예약 가능 기간 | 30일 전까지 제안, 최소 사전 시간은 정책 설정 | 고객 웹 공개 전 |
| 유아·아동 | 총 인원·실제 좌석 필요 수·요금 대상 인원 구분 | 고객 웹 공개 전 |
| 최소소비 | 적용 단위·면제 대상·서비스료·예약금 포함 여부 확정 | 금액 정책 활성화 전 |
| 예약금·취소·환불 | 금액, 기한, 계산 기준, 수수료 부담 확정 | 결제 활성화 전 |
| 개인정보·통화 보관 | 기간·열람 권한·삭제·법적 보존 예외 확정 | 해당 정보 수집 전 |
| 운영 연락 담당자 | 장애·결제 불일치·환불 실패 담당자 지정 | 내부 운영 전 |

실제 테이블 목록·좌석 수·결합 조합·영업시간은 운영자에게 받아야 한다. 예시 테이블이나 가짜 연락처를 운영 DB에 자동 삽입하지 않는다.

## 반드시 확인할 연동 사실

- TeamPlus·EVERY8D 등 업체 이름만으로 SMS API 지원을 가정하지 않는다. 공식 API, 발신자 규칙, 응답 코드, 발송 결과 조회·콜백, 한도와 계약을 확인한다.
- LINE 메시징과 LINE Pay는 별도 연동이다. 결제사 선정 전에는 공통 Adapter와 sandbox 테스트를 준비한다.
- 기존 전화번호·遠傳 계약에서 착신전환/SIP가 가능한지, 발신번호 전달과 직원 연결·동시 통화가 가능한지 통신사 확인이 필요하다.
- 관리자 화면의 전화 연결 방식 선택만으로 통신사 설정이 바뀌지는 않는다. 설정됨·검증됨·장애 상태를 구분한다.
- API 주소는 일반 관리자가 임의 URL을 입력하게 하지 않는다. 승인된 제공업체와 endpoint 목록을 사용하여 내부망 요청·비밀 유출을 방지한다.

## 필드 인수 시나리오

1. 직원 두 명과 웹 고객이 마지막 테이블을 동시에 예약한다. 한 건만 좌석을 확보한다.
2. 결합 테이블 예약이 있는 시간에 구성 테이블의 개별 예약을 시도한다. 거부된다.
3. 고객이 지각하거나 이용시간을 초과한다. 다음 예약 영향과 직원 조치가 표시된다.
4. 예약금 결제 직후 브라우저를 닫는다. 서버 결제 결과로 정확히 확정된다.
5. 결제 기한이 지난 뒤 성공 콜백이 도착한다. 중복 좌석 없이 환불 작업이 생성된다.
6. 휴무와 테이블 고장을 등록한다. 영향 예약이 표시되고 일괄 자동 취소되지 않는다.
7. SMS 실패 중 예약한다. 예약은 유지되고 고객 화면과 직원 연락 작업으로 확인 가능하다.
8. 인터넷 중단 상황에서 당일 예약표로 운영한 뒤 수기 예약을 복구 입력한다. 충돌을 사람이 해결할 수 있다.
9. 잘못된 No-show를 복구한다. 이미 다른 예약이 확보한 좌석을 덮어쓰지 않는다.
10. DB 백업을 별도 환경에 복원한다. 예약·정책·결제 이력·점유 관계가 일치한다.

## 운영 준비 기준

가용성 목표·부하 목표·백업 보존 기간은 운영 규모에 맞게 확정한다. 초기 제안은 RPO 15분 이내, RTO 2시간 이내이며 관리형 PostgreSQL의 PITR 지원과 실제 복원 측정으로 검증한다. RPO는 허용 가능한 데이터 손실 시간, RTO는 복구 목표 시간이다. 이 수치를 달성하지 못하면 실제 측정값과 필요한 인프라 조치를 명시한다.

수기 운영 중에는 온라인 예약과의 충돌 가능성을 직원에게 명확히 표시한다. 별도 접근 경로가 있을 때만 온라인 접수를 일시 중지하며, 연결되지 않은 단말이 중앙 예약 상태를 바꿨다고 표시하지 않는다. 출력물은 직원만 접근하고 정해진 기간 후 폐기한다.
