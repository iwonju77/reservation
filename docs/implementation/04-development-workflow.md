# Codex 직접 개발 절차

## 실행 방식

이 문서는 이 채팅에서 Codex가 저장소를 직접 구현할 때 적용한다. 외부 에이전트에게 전달하거나 외부 실행 승인 이벤트를 기다리는 단계는 없다. 개발은 사용자의 구현 요청 범위 안에서 진행하며, 환경 자체의 권한·보안 요구는 그대로 따른다.

현재 요청의 산출물은 개정 설계서다. 앱 구현에 착수할 때는 아래 절차를 따른다. 이 문서의 TODO를 실제 실행 없이 완료로 바꾸지 않는다.

## 1. 시작 시 확인

1. `/workspace/reservation`의 AGENTS.md, Git 상태, 최신 변경과 이 문서 묶음을 읽는다.
2. 원격 변화와 로컬 사용자 변경이 있으면 보존한다. 기존 checkout을 사용하며 별도 worktree는 명시적인 요청이 있을 때만 만든다.
3. `05-progress.md`에서 다음 단계와 blocker를 확인한다.
4. Node.js·pnpm·PostgreSQL·실행 환경을 검사하고 필요한 지원 버전을 선택해 ADR과 lockfile에 기록한다.
5. 필요한 설정 이름과 사용 가능 여부를 확인한다. 비밀값을 출력하지 않는다.

## 2. 구현 반복 단위

`기능 계약 확인 → DB/API/화면 구현 → 해당 테스트 → 실행 검증 → 진행표 갱신`을 한 단위로 진행한다.

- 한 번에 끝까지 검증 가능한 흐름을 만든다. DB/API 없이 화면만 만든 경우 기능 완료로 기록하지 않는다.
- 먼저 M0와 M1을 진행하고 실제 직원 예약 E2E가 통과한 뒤 고객 웹을 확장한다.
- 설치·로컬 수정·개발 DB migration·테스트는 구현 범위 안에서 계속 진행한다.
- UI에서 숨긴 기능도 서버가 요청을 차단해야 한다.
- 같은 동작을 웹·직원·전화 AI에 중복 구현하지 않는다.
- 테스트 실패를 수정하고 원인을 기록한다. 외부 조건이 필요한 항목만 BLOCKED로 두고 독립 작업은 계속한다.

## 3. 로컬 환경과 외부 기능

로컬 개발은 PostgreSQL과 fake 제공업체로 재현 가능하게 한다. fake 모드에서 실제 문자·결제를 발생시키지 않는다. 비밀 아닌 모드 설정과 환경변수 이름을 `.env.example`에 설명한다.

외부 업체가 정해지면 공식 명세를 확인해 Adapter를 구현하고 sandbox와 실계정 검증을 분리한다. 필요한 계정이나 계약이 없으면 정확한 대상·용도·검증 명령을 기록한다. 운영자가 정할 실제 요금·환불·보관기간은 예시 데이터로 대신 확정하지 않는다.

## 4. 검증과 완료 기록

단계별 계획의 명령 인터페이스를 실제 package script로 구현한다. lockfile이 없는 최초 scaffold에서는 정상 설치로 생성한 뒤, 이후 재현 설치와 CI는 frozen-lockfile을 사용한다.

예약 엔진·좌석 제약·웹훅·금액 처리는 단위 테스트와 실제 PostgreSQL 통합 테스트를 실행한다. 고객·직원 전체 흐름은 E2E로 확인한다. 문서만 변경한 경우 링크와 변경 정합성을 확인한다.

```text
단계 / 마일스톤:
상태: DONE / IN_PROGRESS / BLOCKED
변경 파일:
실행 명령 / 종료 코드:
테스트 수: passed / failed / skipped
검증 환경: local / fake / sandbox / production
실행 확인 결과:
미검증 항목 / 외부 준비사항:
다음 작업:
```

진행표의 DONE은 해당 범위의 실제 검증을 뜻한다. 개발 완료·실연동 완료·운영 출시를 구분한다. 세션 종료 시 실패 원인과 재개 위치를 기록한다.

## 5. Git과 배포

커밋에는 해당 작업의 코드·migration·테스트·문서만 포함한다. 사용자 요청으로 커밋·푸시할 때 원격의 최신 상태를 확인하고 강제 덮어쓰기를 하지 않는다. 클라우드 환경 게시, GitHub push, 애플리케이션 배포는 각각 별도 작업이다.

실제 고객 메시지·금전 거래·운영 DB 변경·외부 공개는 해당 작업이 승인된 범위인지 확인한 뒤 수행한다. 범위 밖이면 검증된 산출물과 구체적인 실행 대상을 준비해 필요한 지시를 받는다. 운영 승인을 개발 시작 조건으로 옮겨 놓지 않는다.

## 6. 다시 시작할 때

최근 Git 변경과 `05-progress.md`를 먼저 읽고 가장 앞선 미완료 단계부터 이어간다. 이미 끝난 작업은 변경된 코드·환경의 영향 범위만 재검증한다. 임의의 stage 파일이나 외부 publication 상태 대신 현재 저장소의 구현·테스트 증거를 기준으로 판단한다.
