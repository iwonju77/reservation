# 단계별 구현 실행 계획

## 진행 규칙

순서대로 수행한다. 각 단계는 체크리스트 구현 → 테스트 → 문서 갱신 → 진행 기록 순서로 마무리한다. 완료 조건을 충족하면 다음 단계로 진행하고, 실패하면 원인을 해결한다. 외부 자격증명이 없으면 독립적으로 가능한 작업을 계속하되 관련 실연동은 BLOCKED로 기록한다.

아래 명령은 Step 01에서 실제 package script로 만들 표준 인터페이스다. 이 문서 작성 시점에 명령이나 구현이 존재한다는 뜻은 아니다.

```text
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test:unit
pnpm test:integration
pnpm test:e2e
pnpm build
pnpm db:migrate:deploy
pnpm db:seed:dev
pnpm dev
pnpm worker:dev
```

통합/E2E 테스트는 격리된 PostgreSQL DB를 사용한다. 테스트 DB 이름·환경을 확인하는 보호장치를 두고 운영 DB 초기화 명령을 테스트에서 실행하지 않는다. `db:seed:dev`는 개발 환경 전용이며 운영에서는 실패해야 한다.

필수 검증:
- [ ] 단 하나의 가능한 테이블에 20개 동시 요청: 정확히 1개 점유 성공, 나머지는 충돌 처리.
- [ ] T01+T02 예약과 T01 단독 예약 경쟁: 두 예약이 동시에 성공하지 않음.
- [ ] 종료와 시작이 같은 시각은 허용, 정리시간이 겹치면 거부.
- [ ] 동일 멱등키 재시도는 같은 예약, 다른 payload는 충돌.
- [ ] 만료 처리와 제출 경쟁에서 일관된 한 결과만 발생.
- [ ] 정책 게시·차단 등록과 예약 생성 경쟁에서 비활성 좌석/금지 시간 확정 없음.

완료 조건: 실제 PostgreSQL 다중 연결 테스트 통과. 다음 UI 단계로 넘어가기 전에 이 단계의 실패를 해결.

- [ ] 조건 일치 중 접수 순서로 후보 선정, 실제 좌석 기한부 확보.
- [ ] 발송 확인 후 응답 기한 시작, 발송 지연 시 절대 만료 적용.
- [ ] 수락 시 예약 HOLD로 점유 소유권을 원자적으로 이전, 필요한 승인·결제 적용.
- [ ] 만료 후 다음 고객 제안, 중복 제안·중복 수락 방지.

검증: 수락과 만료 동시 실행, 같은 좌석에 중복 제안, 발송 실패·결과 불명, 결합 테이블 제안, 예약금 필요 고객 수락.

완료 조건: 실제 확보하지 않은 좌석을 확정 가능한 제안으로 발송하지 않음. 발송 지연으로 좌석이 무기한 묶이지 않음.

## Step 12 — 운영 안정성·개인정보·배포 준비

의존성: 06. B 출시 전에는 07~11 중 활성화할 기능도 완료.

작업:
- [ ] 비밀정보 관리·교체, 최소 DB 권한, TLS, 로그 마스킹, 접근 통제 확인.
- [ ] 개인정보 보관·익명화·삭제 요청과 결제 보존 예외 작업.
- [ ] health·worker·작업 지연·결제 불일치·발송 실패 모니터링과 담당자 연결.
- [ ] 관리형 DB 백업·PITR, 별도 환경 복원 수행과 RPO/RTO 측정.
- [ ] staging/prod 분리, 비파괴 migration, 배포 전 점검, 이전 앱 버전 복구 절차.
- [ ] 데이터 삭제를 동반하는 down migration을 일반 rollback으로 사용하지 않음.
- [ ] 장애 대응 runbook: DB 장애, worker 중단, SMS 장애, 결제 장애, 인터넷 중단, 비밀정보 유출.
- [ ] 필요한 실제 매장 데이터 입력·검증 도구, 초기 계정 안전한 발급.

검증: 복원 DB에서 예약·점유·정책·결제 관계 확인, worker 재시작 복구, 제공업체 중단 중 예약 상태 일관성, 개인정보 로그 검사, 배포 migration 리허설.

완료 조건: 복구 명령 문서만 있는 상태가 아니라 실제 복구 결과가 있음. 운영자의 정책·보관기간 미확정 항목은 출시 blocker로 기록.

## Step 13 — 현장 인수·제한 운영·웹 공개

의존성: 12와 출시 범위 기능.

작업:
- [ ] `01-field-review.md`의 10개 인수 시나리오를 직원과 수행.
- [ ] 실제 매장 테이블·영업시간·특별일·가격을 운영자와 대조.
- [ ] 전 직원 로그인·권한·지각·No-show·고장·취소·환불 교육.
- [ ] staging에서 합의한 부하 목표 테스트. 초기 실험은 동시 조회 50명·예약 명령 10개에서 시작하고 p95·오류율 기록; 운영 목표로 확정된 수치와 구분.
- [ ] 내부 운영 → 제한 고객 → 고객 웹 공개 순으로 rollout 계획과 중단 기준 작성.
- [ ] 중복 배정, 금액 불일치, 예약 확정 실패가 확인되면 신규 접수를 제한하고 원인·영향 예약 처리.
- [ ] 공개 후 점검 책임자와 첫 영업일 점검표 지정.

완료 조건: 출시 체크리스트에 실제 담당자·일시·결과가 있음. 구현 에이전트는 검증된 배포 산출물을 준비하고 실제 운영 공개는 운영자가 확정한 범위에서 수행.

## Step 14 — 전화 AI·추가 채널

의존성: B 단계의 안정 운영 또는 동등한 staging 전체 검증.

작업:
- [ ] 통신사·번호 연결 방식·제공업체·동시 통화·직원 연결 가능 여부 확인.
- [ ] 공식 SDK/API 기반 음성 webhook 인증·재전송·통화 ID 멱등 처리.
- [ ] 예약 검색·제출·조회·변경 명령을 공통 API에 연결. AI가 DB를 직접 수정하지 않음.
- [ ] 날짜·시간·인원·연락처·조건 확인, 승인/결제/확정 구별 안내.
- [ ] 예약 조회·취소의 고객 확인을 발신번호만으로 대체하지 않음.
- [ ] 인식 불확실·지원 언어 외·서비스 장애·직원 연결 실패 시 fallback과 콜백 작업.
- [ ] 녹취 동의·보관·접근 정책 적용, 안내 문구 버전 관리.
- [ ] LINE 메시징·LINE Pay 등 추가 채널은 별도 Adapter와 독립 검증으로 확장.

검증: 실제 시험 통화, 시끄러운 환경·날짜 모호함·중간 종료·재통화·중복 도구 호출·직원 부재, 웹과 동시 마지막 좌석 요청. 예약 API 응답 없이 AI가 확정 안내하지 않는지 평가.

완료 조건: 실제 연결과 fallback이 검증됨. 계정·통신사 기능이 없으면 모의 통화만 완료했다고 기록하고 전화 자동접수는 OFF.
