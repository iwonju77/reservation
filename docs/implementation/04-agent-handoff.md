# 가재코드에 전달할 실행 지시문

아래 블록을 가재코드의 작업 지시문으로 전달한다. 문서 폴더 전체가 작업 저장소에 있어야 한다. 가재코드의 구체적인 제품·버전이나 도구 전용 문법은 가정하지 않았다.

```text
서울아저씨 예약 시스템을 실제로 구현하라.

먼저 docs/implementation/README.md와 01~05 문서를 모두 읽어라.
이 문서 묶음은 구현 계약과 단계별 완료 기준이다.
기존 저장소 코드·AGENTS.md·사용자 변경을 확인하고 현재 상태에 맞춰 진행하라.
각 작업은 이미 격리된 환경의 기존 checkout에서 수행한다.
사용자가 명시적으로 요청하지 않았다면 새 Git worktree를 만들지 마라.

Step 00부터 순서대로 구현·검증하라. 기존 구현이 있으면 계약과 테스트로
검증한 뒤 재사용한다. UI만 만들거나 계획만 다시 작성하고 끝내지 마라.
단계 완료 후 결과를 docs/implementation/05-progress.md에 기록하고
다음 독립적으로 수행 가능한 단계로 계속 진행하라.

합리적인 기술 선택은 문서 기본안을 사용하고 결정 근거를 ADR에 기록한다.
운영자가 결정해야 할 실제 가격·테이블·환불·개인정보 보관 정책을
확정된 사실로 꾸미지 마라. 개발 fixture로 진행하고 운영 공개 전 blocker로 남겨라.

웹·직원·전화 AI의 예약 명령은 하나의 도메인 서비스를 사용한다.
PostgreSQL의 점유 제약과 실제 다중 연결 테스트로 중복 예약을 방지한다.
결제·예약·환불·알림 상태를 분리하고, 멱등성과 만료 경합을 검증한다.
정책 스냅샷과 변경 이력을 유지하며 설정 변경으로 기존 예약을 조용히 수정하지 마라.
같은 테이블의 부분 중첩 예약 변경도 테스트하라.

도메인 단위 테스트, 실제 PostgreSQL 통합 테스트, 고객·직원 E2E를 작성하라.
실패하거나 실행하지 않은 테스트를 통과했다고 기록하지 마라.
mock·sandbox·실제 업체 검증을 분리하라. 외부 API와 웹훅 형식을 추측하지 말고
선정된 업체의 공식 명세를 확인하라.

비밀정보를 코드·채팅·로그·문서에 넣지 마라. 환경변수 이름과 요구 목적만 문서화한다.
기존 인증과 환경 구성을 확인하고, 필요한 키는 보안 설정으로 제공받는다.
키가 없으면 fake Adapter·오류 처리·문서·독립 기능을 계속 구현하고
실연동만 BLOCKED로 표시하라. 활성 필수 정책을 건너뛰어 출시하지 마라.

설치·로컬 수정·테스트·문서화는 계속 진행한다. 실제 고객 알림, 실제 금전 거래,
운영 데이터 변경, 외부 공개는 기존에 승인된 범위인지 확인하고, 범위 밖이면
구체적인 산출물·검증 결과·대상·영향을 준비한 후 필요한 승인을 요청하라.
일반적인 로컬 개발 작업마다 재확인을 요구하지 마라.

운영자에게 넘길 결과에는 변경 파일, 실행법, 테스트 결과, 남은 blocker,
출시 가능한 범위, 다음 작업을 포함하라. 작업이 중단되면 진행표와 재개 지점을
갱신하여 다음 세션이 같은 조사를 반복하지 않게 하라.
문서와 실제 구현이 달라지면 이유를 기록하고 계약·테스트·운영 문서를 함께 갱신하라.
```

## 외부 준비사항 요청 형식

한 번에 필요한 항목을 모아 아래 형식으로 요청한다. 비밀값을 채팅으로 요청하지 않는다.

```text
필요 항목:
용도 / 막힌 단계:
이미 확인한 기존 설정:
보안 설정에 입력할 변수 이름:
비밀 아닌 운영자 결정사항:
값 없이 완료한 작업:
값 제공 후 실행할 검증:
```

## 단계 완료 보고 형식

```text
단계:
상태: DONE / IN_PROGRESS / BLOCKED
변경 파일:
실행 명령과 결과:
검증 환경: local / fake / sandbox / production
테스트 수: passed / failed / skipped
수동 검증 결과:
남은 제한사항:
다음 단계:
```

## 재개 지시문

```text
docs/implementation/05-progress.md와 최근 Git 변경을 먼저 확인하라.
완료된 단계는 증거를 읽고, 코드나 환경이 바뀐 부분만 필요한 범위에서 재검증하라.
가장 앞선 미완료 단계와 그 blocker를 확인한 뒤 독립적으로 가능한 작업을 계속하라.
진행표의 상태만 믿고 테스트 결과를 만들어내지 마라.
```
